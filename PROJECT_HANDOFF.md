## Hardware and wiring notes

- Breadboard: CN2 pin 4 3.3 V to red rail; CN2 pin 6 GND to blue rail.
- Potentiometer: 10 kΩ between rails; wiper to CN4 pin 1 PC5/A0. The wiring SVG shows the recommended 100 nF capacitor from PC5/wiper to GND.
- Start/cancel button: CN3 pin 3 PD14/D2 to momentary switch to GND.
- Strength selector: three-terminal, two-position SPDT. Identify COM with a continuity meter, wire COM to CN3 pin 5 PA3/D4, one outer throw to GND, and leave the other throw unconnected. Move the GND lead to the other throw if the lever direction maps to the wrong mode.
- Green/yellow/red LEDs: CN3 pins 6/7/8 (PB4/PB1/PA4), each with its series resistor (150/330/330 Ω) and cathode to GND.
- The VL53L0X sensor and PC13 user button are onboard; do not wire them to the breadboard. The wiring diagram labels the onboard PC13 pull-up and capacitor network.
- Wire while the board is unplugged. Use printed header labels rather than counting pins from a drawing.

## Current code changes

- Added HAL-free FSM API and implementation: `FinalProject_STM32/Inc/coffee_sm.h` and `FinalProject_STM32/Src/coffee_sm.c`.
- FSM covers standby, idle, heating, three brew phases, complete, latched faults, cancel, fault recovery, LED patterns, and simulated actuator requests.
- Added `FinalProject_STM32/Src/coffee_app.c` and `Inc/coffee_app.h` as the superloop integration path. It qualifies PC13/PD14 buttons and PA3 strength switch, filters PC5 ADC and maps it to a simulated 20–110 °C temperature, reads VL53L0X distance through the STM32Cube L4 vendor PAL/API in `VL53L0X_DEVICEMODE_SINGLE_RANGING` (not gesture mode), applies saved cup-detection thresholds with 80/100 mm defaults and hysteresis, rejects zero-mm samples as invalid, maps FSM LED patterns to PB4/PB1/PA4/PB14, and emits periodic USART1 telemetry.
- The board's 8 MB Macronix MX25R6435F QSPI flash is accessed by `Src/qspi_flash.c`. Sectors 1–2 (0x1000/0x2000) are alternating CRC-protected ToF cup-detection profile slots; sector 0 is untouched. Sectors 3–15 hold the CRC-protected 32-byte event ring. `Src/storage_manager.c` scans the event ring and stores boot/state/fault records. `flash=OK/NO` reports whether the QSPI interface initialized, not recent read/write health; `logger=OK/NO` reports event append availability. A logger write failure no longer disables reads, and the app retries logger initialization every 5 seconds. Event-log enumeration, recovery scans, and streamed slot searching now process at most 8 slots per coffee-app pass. The host command `CMD,READ_LOGS` streams `LOG_SCAN` / `LOG_BEGIN` / `LOG` / `LOG_END` lines over USART1. The Python GUI displays them and saves CSV. Log retrieval still needs hardware validation. The QSPI clock prescaler is 3 (20 MHz from the 80 MHz AHB clock).
- Latest QSPI log fix: the user observed that after a fault they had to press the black reset button before the GUI could retrieve logs. Fault state does not stop the app task or USART1 polling. The likely failure path was an event append error (often the fault event itself) setting `storage_available=false`; `Storage_ReadLogSlot()` incorrectly used that writer-health flag as its read gate. Reads now gate on `QspiFlash_IsAvailable()`, while appends still gate on successful storage initialization. Firmware retries event-logger initialization every 5 seconds. GUI telemetry validation requires `logger`, and the note differentiates QSPI online from event logger retrying. Rebuild/reflash firmware and restart the GUI before hardware validation. Do not claim hardware verified until log retrieval succeeds after a fault without resetting.
- Follow-up from review: QSPI log enumeration, logger recovery scans, and streamed slot searching were converted to bounded 8-slot steps in the coffee-app task, so scans yield to sensor sampling, FSM, outputs, and telemetry. GUI labels `flash=OK` as “QSPI interface initialized,” not as current I/O health; an individual read failure remains visible in the log request result.
- These follow-up edits have not yet been rebuilt or verified on hardware. Rebuild the STM32 project and run the GUI syntax check before flashing; then test QSPI retrieval in STANDBY and after inducing a fault without pressing reset.
- Latest user report: one QSPI read succeeded, then subsequent requests timed out with **no response**, even after the board reset. This differs from a flash read failure: firmware sends `LOG_SCAN` as soon as it parses `CMD,READ_LOGS`, before accessing QSPI. No acknowledgment therefore points to USART command reception, a stalled/non-coffee firmware image, or a stale COM connection. The GUI timeout now distinguishes live STATUS telemetry with no command acknowledgment from no USART traffic. During next reproduction, note whether the main dashboard continues to show LIVE telemetry after the log request times out; this separates a command receive-path problem from a link/firmware stall. The QSPI read command itself does not modify flash.
- Latest ToF calibration output: clear and removed stages each had `range_ok=0/10`, with samples alternating between status 0 / 0 mm and status 4 / 8190 mm; cup stage was valid at a 31 mm median. ST's VL53L0X API defines RangeStatus 4 as Phase Fail (not a valid distance); 8190 must not be interpreted as 8190 mm. Status 0 means API range-valid, but 0 mm is rejected by our app/calibrator as an unusable zero-distance sample. The stage's `median_mm=0` is the code's empty-valid-sample sentinel, not a measured median. Calibration still passed because when both clear/remove stages have zero usable ranges it intentionally assumes clear reference = cup median + 60 mm, yielding 51/71 mm thresholds from the 31 mm cup median. Therefore the saved result used `CUP_PLUS_60MM_FALLBACK`, not a measured clear distance. Future calibration output now prints `median_mm=NA` when no usable samples exist and includes threshold basis plus valid range counts in the PASS line. Rebuild/reflash calibration mode to see this clearer output. The previous PASS profile was written to QSPI sectors 1–2.
- Wire protocol: host sends `CMD,READ_LOGS\r\n`; coffee-app firmware responds with `LOG_SCAN`, then `LOG_BEGIN,count=N`, one `LOG,seq=...,tick_ms=...,event=...,state=...,fault=...,temp_x10=...,cup_mm=...,strength=...,flags=...,heater=...,pump=...,crc=...` per CRC-valid record, then `LOG_END,count=N`. Errors use `ERR,code=...`. Records are streamed one per app pass so input/state work and STATUS reports continue during download. The GUI sorts by sequence, offers **Save CSV**, and times out with a mode hint if no scan response arrives.
- Copied the STM32Cube L4 VL53L0X source into `FinalProject_STM32/Drivers/BSP/Components/vl53l0x` and added its include path to both IDE configurations. Corrected the vendor HAL receive address to use the 7-bit address shifted as expected by STM32 HAL. The user reports the current build target completes and the ELF contains application and VL53L0X symbols; a compile-only syntax check also passes. Coffee-mode hardware ranging remains unverified.
- Coffee application selection is wired into the `main.c` user-code hooks. Current source settings are `IO_TOF_CALIBRATION_MODE=0`, `IO_DIAGNOSTICS_MODE=0`, selecting coffee mode. The ToF driver resets XSHUT and retries sensor initialization every 2 seconds after repeated I2C/API failures. Only API/bus failures count toward the SENSOR_COMM fault; a successful API call with a nonzero range status or zero-mm result is treated as no usable target, not a communication fault. Invalid readings clear distance/cup-present and telemetry reports `cup_valid=0`; during active brewing, invalid cup readings count toward the no-cup safety timeout. USART1 carries telemetry and the read-only QSPI log request; it has no coffee-state/actuator command interface. Tank-empty remains false because this hardware design has no tank-level sensor. Heater/pump outputs remain simulated requests and are not connected to mains hardware.
- Added a dedicated interactive ToF cup-detection calibration mode in `Src/tof_calibration.c`, selectable by setting `IO_TOF_CALIBRATION_MODE=1` while keeping diagnostics mode 0. It performs single-shot ranging, captures ten samples with the sensor view clear, then prompts over USART1 to place a cup and remove it (press Enter at each prompt; CR, LF, and CRLF are supported). It reports API status, range status, millimeters, and stage medians. On a successful separation check, it derives present/absent thresholds and stores the profile with CRC/read-back verification in alternating QSPI sectors 1–2, preserving the last valid profile if an update is interrupted. `CoffeeApp_Init()` loads the newest valid saved profile; otherwise it uses default 80/100 mm thresholds. STATUS telemetry includes active thresholds. Set calibration mode back to 0 and keep diagnostics mode 0 to run the coffee application after calibration. Calibration and QSPI persistence are implemented in source but not hardware-tested yet.
- `main.c` was changed only inside the CubeMX `USER CODE BEGIN 3` loop area for watchdog refresh; generated peripheral initialization was not edited.
- Added `Src/io_diagnostics.c` and `Inc/io_diagnostics.h`; diagnostics are selectable with `IO_DIAGNOSTICS_MODE 1` and called from the user-code init/superloop hooks in `main.c`. It steps READY/HEATING/FAULT/PB14 LEDs, samples D2/PD14, D4/PA3, onboard PC13 and PC5 ADC, probes I2C2 address 0x29, and sends a 500 ms report over USART1.
- Diagnostics are implemented in source; `io_diagnostics.c` and `main.c` passed a compile-only syntax check. The user reports the diagnostic mode works on the physical setup, including LED cycling, input readings, PC5 ADC, ToF I2C acknowledgment, and USART1 reports. `TOF=ACK` checks only I2C presence, not range data. No coffee FSM or heater/pump commands run in this mode.
